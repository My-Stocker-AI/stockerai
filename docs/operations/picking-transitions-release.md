# Versioned picking transitions

This release extends the atomic item protocol to start, skip, return to skipped work and explicit route reset. New clients use `/api/picking-transition`; `/api/picking-context` provides a read-only initial revision after matching the displayed route and machine list. The existing advancement function executes inside the versioned transaction for next-item commands.

Each request includes the authenticated caller's exact session, a unique operation ID, the displayed machine/count/status/direction, and an opaque route revision. All new transitions lock the route before its session/machines. Successful transitions consume a revision and store their result in the same transaction. Replaying the same operation returns its receipt; reusing a key for different intent conflicts. Machine and session writes invalidate revisions, including legacy writes and resets that return to identical counts. Client-supplied identity cannot override the verified login.

Reset is available only through the existing confirmation dialog. It binds the confirmation to the displayed target, requires route ownership, refuses another active session on that route, sets every machine to pending/zero with cleared skip markers, and reopens the caller's session at the first machine. Local state is cleared only after confirmed success. It does not delete route definitions, uploaded files or operation receipts. The model's tool output alone cannot authorize reset. Undo remains a separate unresolved contract.

Run the full backend suite via `scripts/disposable-db/run-tests.ps1`, frontend tests and production build. Recheck relevant schema/constraints/triggers, service-only grants and recovery availability. The prior release's metadata preflight does not verify this new migration.
3. Following explicit release approval, apply **only** `20260923000000_atomic_picking_transitions.sql`; do not blanket-push historical migrations. This migration adds a route revision column and triggers affecting every machine/session write, so review lock contention and legacy interactions. Verify signatures, function bodies, search paths and browser-role denial from metadata. Do not exercise reset on driver data as a release test.
4. Release API first (including revision-aware resume and direction in route selection), verify the exact Render commit and both new endpoints, then release the client separately and verify the public bundle. Reload/reopen before a new route. Retain the additive schema during application rollback; restore the previous frontend before the previous API. Do not delete operation receipts or reverse route data as a rollback.

Record physical iOS and Android acceptance separately: one/two-item forward/reverse routes, start/skip/back, final-item skip recovery, refresh, lost response, stale second device, Bluetooth interruption, background/lock and touch fallback. Reset acceptance must use explicitly disposable routes, never a driver's real route.

## Boundaries

- Revision checks prevent old new-protocol commands from silently acting on changed state; they do not make every legacy writer transactional. Existing old clients/endpoints, route selection, upload replacement, deletion and session-status changes retain their earlier multi-write behavior. Legacy writes can conflict or deadlock with route-first transactions; PostgreSQL aborts a participant, and the client must reload rather than automatically replay. Retiring/upgrading those writers and load testing remain necessary before closing finding 09.
- The first adoption by an older client without a revision matches the currently displayed full machine list to saved state. It cannot prove that an identical state was never reached through earlier changes. Subsequent responses and local persistence retain revisions; a deliberate authoritative reload adopts the new snapshot.
- No automatic replay or durable outgoing-operation queue is introduced. Missing responses require saved-state recovery. Receipts still have no periodic retention policy.
- Counts remain presented-item counts. A same-direction start on an in-progress machine reannounces without advancing; changing direction on an in-progress machine conflicts. A skipped fully presented machine reannounces its final window so completion remains possible. Durable confirmed-versus-presented semantics and exact two-item restoration remain finding 10; per-machine direction history is not added here.
- Reset ownership is a conservative boundary until the unified account capability model is implemented. Teammates may still pick a permitted team route but cannot reset another owner's route through this endpoint.
- Static tests and a successful deployment do not establish microphone/headset or production workload acceptance.
